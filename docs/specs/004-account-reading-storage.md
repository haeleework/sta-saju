# 004-account-reading-storage: 해석 결과의 계정별 데이터베이스 저장

> 브라우저 저장과 병행하던 초기 설계는 2026-09-29에 변경했습니다. 현재는 계정 저장만 제공하며 상세 동작은 `016-account-only-reading-storage.md`를 따릅니다.

상태: 코드·자동 검사·운영 DB 적용 완료 · 실제 계정 격리 검증 전

작성일: 2026-09-23

선행 기능: `002-gemini-reading.md`의 해석 결과, `003-google-login.md`의 구글 로그인

## 목표와 결정

- 로그인한 사용자가 **현재 보고 있는 해석 결과 한 건**을 Supabase Postgres에 저장하고 다른 기기에서 다시 열 수 있게 합니다.
- 사주 서비스는 로그인 후에만 이용하며(`006`), 과거 브라우저 저장 목록을 계정으로 자동·일괄 이전하지 않습니다.
- 로그인 후 만든 결과도 각각 명시적으로 `계정에 저장`을 눌러야 하며, 로그인했다는 이유만으로 자동 업로드하지 않습니다.
- 계정 저장과 브라우저 저장은 독립적입니다. 클라우드 저장 성공 여부를 명확히 보여주고, 기존 브라우저 자료를 삭제하거나 덮어쓰지 않습니다.

## 저장할 자료와 최소 스키마

기존 `SavedReading`의 성공한 필드만 보냅니다. 원본 생년월일·출생시간, Google 이메일·이름, Gemini API 키와 인증 토큰은 결과 테이블에 저장하지 않습니다. 다만 사주 구성과 해석 자체도 개인과 연결될 수 있으므로 비공개 자료로 취급합니다.

| 필드 | 형식·규칙 | 목적 |
|---|---|---|
| `id` | `bigint generated always as identity`, 기본키 | 데이터베이스 내부 식별자 |
| `user_id` | `uuid not null`, `auth.users(id)` 참조, 사용자 삭제 시 함께 삭제 | 소유자 구분 |
| `source_id` | `uuid not null`, 현재 결과의 `SavedReading.id` | 같은 저장 요청의 중복 방지 |
| `interpreted_at` | `timestamptz not null` | 결과가 처음 생성된 시각 |
| `saved_at` | `timestamptz not null default now()` | 계정에 저장된 시각·목록 정렬 |
| `updated_at` | `timestamptz not null default now()` | 주제 해석 추가·수정 시각 |
| `schema_version` | 정수, 최초 값 `1` | 향후 결과 형식 변경 구분 |
| `chart` | `jsonb not null`, 객체 | 계산된 년·월·일·시주와 계산 기준 |
| `base_reading` | `jsonb not null`, 객체 | 검증된 기본 AI 해석 |
| `topic_readings` | `jsonb not null default '{}'`, 객체 | 성공한 관심 주제별 해석 |

- 테이블 이름은 `public.saju_readings`를 제안합니다. `(user_id, source_id)` 유일 제약으로 중복 저장을 막고, `(user_id, saved_at desc)` 인덱스로 본인 목록 조회와 사용자 삭제 시 참조 확인을 빠르게 합니다. `chart`, `base_reading`, `topic_readings`는 객체인지 검사하고 앱에서도 기존 해석 파서로 구조·길이를 검증합니다.
- `source_id`는 현재 코드가 생성하는 UUID입니다. 다른 계정에서 우연히 같은 값이 있어도 각자 저장할 수 있도록 유일 범위는 사용자별로 둡니다.
- 스키마와 권한은 구현 시 검토 가능한 변경 파일로 관리하고, 실제 적용 전 기존 테이블·권한·Data API 설정을 확인합니다. 이 문서는 SQL을 실행하지 않습니다.

## 사용자 흐름과 동기화 규칙

1. 기본 해석이 성공한 **현재 결과**에 `계정에 저장`을 표시합니다. 주제 해석이 이미 있으면 함께 저장합니다. 실패·미완성 해석은 보내지 않습니다.
2. 서비스 입장 전에 로그인하므로 `계정에 저장`에서 별도 로그인 복귀는 필요하지 않습니다. 과거 목록은 훑거나 업로드하지 않습니다.
3. 저장 성공 응답을 받은 뒤에만 `계정에 저장됨`을 표시합니다. 계정 저장 목록에서 생성 시각과 일주를 보여주고, 선택하면 계산 결과·기본·주제별 해석을 다시 엽니다. 페이지 단위로 본인 자료만 최신 저장순으로 읽습니다.
4. 동일 결과에서 새 주제 해석이 성공하면 그 결과가 이미 계정에 저장되어 있는 경우에만 해당 행을 갱신합니다. 저장한 결과를 다른 기기에서 열어 새 주제를 생성하려면 원본 입력을 다시 받고 서버에서 계산한 구성이 저장된 구성과 일치하는지 확인합니다. 원본 입력은 저장하지 않습니다.
5. 계정 결과를 삭제할 때는 대상·저장 시각을 표시해 확인받고 해당 계정 행만 삭제합니다. 브라우저의 별도 로컬 결과는 자동 삭제하지 않습니다.

## 접근 제한과 개인정보

- `public.saju_readings`에 행 단위 보안(RLS)을 켭니다. `anon` 역할의 테이블 접근 권한은 제거하고, `authenticated`에는 필요한 `SELECT`, `INSERT`, `UPDATE`, `DELETE`만 부여합니다. 현재 Supabase 프로젝트의 Data API 노출·기본 권한 상태도 구현 전에 확인합니다.
- 각 작업의 RLS 정책은 `user_id = (select auth.uid())`를 요구합니다. `INSERT`에는 `WITH CHECK`, `SELECT`·`DELETE`에는 `USING`, `UPDATE`에는 `USING`과 `WITH CHECK`를 모두 적용해 다른 사용자의 행을 읽거나 소유자를 바꾸지 못하게 합니다. 앱의 화면 필터만으로 보안을 대신하지 않습니다.
- 브라우저에는 공개 가능한 publishable key와 사용자 세션만 사용합니다. `service_role`/secret key로 사용자 대신 데이터베이스를 읽거나 쓰지 않습니다. 사용자가 보낸 `user_id`·행 ID만 믿지 않고 RLS로 최종 제한합니다.
- 계정 결과는 새로운 브라우저의 `localStorage`에 자동 복사하지 않습니다. 로그아웃·계정 전환 시 화면에 남은 계정 목록과 메모리 캐시를 비웁니다. 기존 로컬 결과는 브라우저 자료로 별도 표시하고 공용 기기에서 보일 수 있음을 알립니다.
- 원본 입력은 Gemini 요청·브라우저 저장과 마찬가지로 계정 결과 테이블에도 저장하지 않습니다. 삭제·보존 기간 정책은 공개 운영 전에 결정합니다.

## 실패·재시도

- 인증 만료·로그아웃: 계정 저장·조회·삭제를 실행하지 않고 사주 화면을 숨긴 뒤 재로그인을 안내합니다. 브라우저의 기존 저장값 자체는 삭제하지 않습니다.
- 네트워크·권한·저장 공간 오류: `계정에 저장되지 않았습니다`라고 표시하고 재시도할 수 있게 합니다. 실패를 성공으로 표시하거나 로컬 자료를 삭제하지 않습니다.
- 응답을 받지 못했지만 서버 저장 여부가 불확실한 경우: `(user_id, source_id)`로 본인 행을 다시 확인한 뒤 재시도합니다. 유일 제약을 이용해 같은 결과가 두 건 생기지 않게 합니다.
- 손상되거나 구버전인 로컬 결과는 임의로 업로드하지 않습니다. 읽을 수 없는 클라우드 결과는 목록 전체를 멈추지 않고 오류 항목을 구분해 안내하며 원본 행을 자동 수정·삭제하지 않습니다.
- 주제 갱신 실패 시 기존 계정 결과는 그대로 두고 실패한 주제만 다시 시도합니다.

## 이번 범위에서 제외

과거 `localStorage` 목록 이전, 자동 업로드·자동 양방향 동기화, 타인과 공유, 결제, 자유 질문, 원본 생년월일·출생시간의 계정 저장. 데이터베이스 백업·계정 삭제 화면은 공개 운영 전에 별도 Spec으로 정합니다.

## 완료 조건과 검사

1. 비로그인 상태에서는 사주 서비스를 이용할 수 없습니다. 저장 버튼을 누른 현재 결과만 계정에 한 건 저장되며, 과거 로컬 목록은 업로드되지 않습니다.
2. 같은 요청을 반복해도 계정에 중복 행이 생기지 않습니다. 기본·주제별 해석이 다시 열리고, 새 주제의 성공한 결과만 해당 계정 행에 반영됩니다.
3. 별도 구글 계정 A·B와 비로그인 상태로 조회·수정·삭제를 시험해 서로의 결과에 접근할 수 없음을 **실제 사용자 권한**으로 확인합니다. 관리자 권한만으로 검사하지 않습니다.
4. 저장 실패·불확실한 응답·세션 만료·삭제 실패를 확인하고, 성공하지 않은 작업을 완료로 표시하지 않습니다. 로컬 결과는 보존됩니다.
5. 데이터베이스 권한, RLS, 유일 제약, 인덱스, Data API 노출 설정을 확인하고 기존 사주 계산·Gemini 해석 검사 및 실제 화면 흐름도 다시 실행합니다.

## 구현 전 확인

- 현재 Supabase MCP 연결이 곧 앱의 Auth·데이터베이스 설정을 뜻하지는 않습니다. 대상 프로젝트와 앱용 URL·publishable key를 구현 전에 확인합니다.
- 공개 운영 전에는 데이터 보존·계정 삭제 요구, 저장 개수·크기 제한, 백업 정책을 결정합니다.

## 검증 결과

- `supabase/migrations/202609230001_create_saju_readings.sql`에 테이블, 사용자별 유일 제약, 최신순 인덱스, `updated_at` 트리거, `anon` 권한 제거, `authenticated` 최소 권한, 작업별 소유자 RLS 정책을 작성했습니다. 2026-09-28 `sta-saju` 운영 Supabase 프로젝트(`fugbpwilyvbigfgbajdv`, 서울 리전)에 SQL Editor로 적용했고 `Success. No rows returned`를 확인했습니다.
- 앱에서 현재 결과의 명시적 저장, 최신순 페이지 조회·더 보기, 재열람, 삭제, 이미 저장한 결과의 주제 해석 갱신을 연결했습니다. 과거 `localStorage` 목록은 읽어 자동 업로드하지 않습니다.
- 같은 `(user_id, source_id)`는 upsert하며, 저장 응답이 유실된 경우 본인 `source_id`를 다시 조회해 성공 여부를 확인합니다. 손상된 클라우드 행은 목록 전체를 막지 않고 제외 사실을 알리며 자동 수정·삭제하지 않습니다.
- 구현을 맡지 않은 테스트 담당이 계정 저장 테스트 11개를 추가했습니다. 행 형식 검사, 키 순서와 무관한 차트 일치, 페이지 조회, 중복 저장, 불확실 응답 재조회, 실패·삭제 처리, 마이그레이션의 RLS·권한·제약을 외부 호출 없이 확인했습니다.
- 주 에이전트 최종 검증에서 `npm run check`의 전체 자동 검사 57개와 `npm run build`가 통과했습니다. Gemini 실제 호출과 실제 Supabase 데이터 변경은 발생하지 않았습니다.
- 운영 DB에서 읽기 전용 카탈로그 검증 12개를 실행해 테이블 존재, RLS 활성화, `anon` 조회·삽입 차단, `authenticated` 조회·삽입·갱신·삭제 권한, 소유자 정책 4개, 사용자별 유일 제약, 최신순 인덱스, `updated_at` 트리거가 모두 `true`임을 확인했습니다.
- 비로그인 및 서로 다른 실제 사용자 A·B로 조회·저장·갱신·삭제 격리를 아직 검증하지 않았으므로 `docs/status.md`의 004는 완료 처리하지 않았습니다.
