# 013-daily-fortune: 내 사주 기반 오늘의 운세

상태: 사용자 흐름·계산 범위 결정 · 운영 비용 상한과 실제 배포 검증 전 · 구현 전

작성일: 2026-09-28

선행 기능: `003-google-login.md`, `004-account-reading-storage.md`, `011-gender-fortune-cycles.md`

## 목표와 사용자 결정

- 로그인한 사용자가 계정에 저장한 사주 결과 중 **하나를 직접 `내 사주`로 지정**하고, 이후 다른 저장 결과로 바꿀 수 있습니다. 최근 저장한 결과가 자동으로 `내 사주`를 바꾸지는 않습니다.
- 매일 한국 시간 기준 오늘의 운세를 미리 만들어 DB에 보관하고, 사용자가 `오늘의 운세 확인하기`를 누르면 **저장된 내용**을 보여줍니다. 버튼을 누를 때마다 Gemini를 새로 호출하지 않습니다.
- 사용자가 단순히 다른 사람의 사주를 시험하거나 계정에 저장했다는 이유만으로 매일 AI 비용이 발생하지 않습니다. `내 사주`를 지정한 계정만 생성 대상입니다.
- 첫 버전은 대운(약 10년 흐름)·세운(올해 흐름)·일운(오늘 흐름)을 모두 반영합니다. 이 계산은 코드에서 하며 **오늘의 운세 생성용 Gemini 요청만** 계정당 한국 날짜 하루 최대 1회입니다. 계산 근거가 늘어 요청당 입력량은 소폭 늘 수 있습니다. 기존 기본 사주·관심 주제 해석 요청에는 이 횟수 제한을 적용하지 않습니다.

## 현재 코드와 선행 변경

- 현재 `public.saju_readings`는 사용자가 명시적으로 저장한 **해석 결과 여러 건**을 보관합니다. `내 사주` 표시나 매일 생성 여부는 없습니다. 원본 생년월일시와 성별도 보관하지 않습니다.
- 기존 대운 계산은 생년월일시와 성별이 필요합니다. 사주 8글자만으로 당시 입력과 대운 시작 시점을 안전하게 복원하지 않습니다. `내 사주`를 처음 지정할 때 양력 생년월일시·성별을 **한 번 다시 입력**받아 기존 저장 결과의 사주 구성과 일치하는지 검사한 뒤 대운을 계산합니다. 원본 입력은 DB에 남기지 않고 계산된 대운 기준만 저장합니다.
- 사용자 본인 결과만 보이는지 두 실제 계정으로 검증하는 기존 `004`의 완료 조건도 이 기능의 배포 전에 확인해야 합니다.

## 사용자 흐름과 화면

1. 로그인 후 계정 저장 결과 목록에서 한 건을 `내 사주로 지정`하고, 그때 원본 생년월일시·성별을 다시 입력합니다. 서버가 재계산한 8글자가 선택한 저장 결과와 다르면 등록하지 않습니다. 지정하지 않았으면 오늘의 운세 카드에 `내 사주를 먼저 지정해 주세요`와 지정 방법을 표시합니다.
2. 화면 상단의 계정 정보 아래 또는 기존 결과 영역보다 앞에 `오늘의 운세` 카드를 둡니다. 카드에는 한국 날짜, 등록 상태와 `오늘의 운세 확인하기` 버튼을 보여줍니다. 버튼은 그날의 저장 결과가 있을 때만 활성화합니다.
3. 버튼을 누르면 오늘의 한 줄, 그렇게 읽은 이유, 오늘 해볼 작은 행동을 쉽고 짧은 한국어로 보여줍니다. 계산으로 확인한 근거와 해석 문장은 구분하고 미래 사건을 확정하지 않습니다.
4. 오늘 결과가 아직 없으면 `오늘의 운세를 준비 중입니다`라고 안내합니다. 전날 결과를 오늘 운세처럼 보여주거나 버튼 클릭만으로 비밀리에 새 AI 요청을 만들지 않습니다.
5. `내 사주`를 바꾸면 변경된 기준은 **다음 예약 생성부터** 적용합니다. 이미 만들어진 오늘 결과는 새 사주의 결과인 것처럼 표시하지 않고, 새 결과를 볼 수 있는 시점을 안내합니다. 해당 저장 결과를 삭제하면 연결된 `내 사주` 지정도 해제합니다.
6. 로그아웃하거나 계정을 바꾸면 이전 계정의 오늘 운세와 메모리 캐시를 즉시 숨깁니다.

## 운세 계산과 AI의 역할

- `lib/saju`가 등록 사주와 오늘 날짜(한국 시간 기준)로 오늘의 간지와 오행·일간 관계를 계산합니다. 등록 시 계산한 대운 기준과 기존 `011`의 규칙으로 현재 대운·세운도 구하고, 세 흐름을 **계산 근거**로 구분해 둡니다. 대운·세운·일운이 같은 방향이라고 해서 특정 사건이 반드시 일어난다고 단정하지 않습니다.
- Gemini는 **계산된 사실을 바꾸지 않고** 읽기 쉬운 문장으로 풀어 씁니다. 기존 `gemini-3.5-flash-lite`와 서버 전용 `GEMINI_API_KEY`를 재사용합니다. 대운을 넣어도 추가 Gemini 호출은 만들지 않고, 한 번의 프롬프트에 필요한 계산 근거만 간결하게 넣습니다.
- 오늘의 운세 생성에 한해 계정당 한국 날짜 하루 **Gemini 요청 최대 1회**와 성공 결과 최대 1건을 지킵니다. 요청 직전에 시도 상태를 영속적으로 선점해, 응답이 유실되거나 Cron이 중복 호출되어도 같은 날 재요청하지 않습니다. 출력은 `summary`, `reason`, `action` 등 고정 형식으로 검증하고 빈 문장·형식 오류·계산과 모순되는 해석은 저장하지 않습니다. 불안감을 주는 예언이나 건강·금전상의 단정적인 지시는 하지 않습니다.
- Gemini에 구글 이메일, 원본 생년월일시, 성별, 인증 토큰을 보내지 않습니다. 필요한 계산 결과와 오늘 날짜만 보냅니다.

## 예약 실행과 실패 처리

- Vercel Cron은 프로덕션의 `GET /api/cron/daily-fortune`를 호출합니다. 한국 오전 9시의 UTC 표현은 `vercel.json`의 `0 0 * * *`입니다. Vercel Hobby 플랜에서는 그 시각이 정확한 9시가 아니라 **9:00~9:59 KST**일 수 있으므로 화면은 `오전 9시부터 순차 준비`로 안내합니다.
- `CRON_SECRET`을 Vercel 서버 환경변수로 설정하고 `Authorization: Bearer ...`를 검사합니다. 값이 없거나 틀리면 실패 상태로 닫고, 비밀값을 응답·로그·브라우저에 노출하지 않습니다.
- Cron은 `auth.users` 전체가 아니라 `내 사주`를 지정한 활성 프로필만 페이지 단위로 조회합니다. 사용자별 작업 상태를 DB에 남겨 중복 호출이나 수동 재호출이 같은 운세를 두 번 생성·과금하지 않도록 합니다. 장시간 실행 한도와 호출량 상한을 적용하고, 넘친 대상은 미처리로 남겨 운영자가 확인·재개할 수 있게 합니다.
- Vercel은 실패한 Cron을 자동으로 재시도하지 않습니다. 실패한 사용자만 식별 가능한 운영 상태(개인 내용 없는 코드·건수)를 남깁니다. 권한이 있는 운영자가 같은 날짜를 다시 실행하더라도 **아직 Gemini 요청을 시작하지 않은 작업만** 처리합니다. 이미 요청한 계정은 그날 다시 호출하지 않고 `오늘의 운세를 만들지 못했습니다`를 보여줍니다. AI 오류를 가짜 운세로 바꾸지 않습니다.
- 한국 날짜는 서버에서 `Asia/Seoul` 기준으로 계산합니다. 자정 경계 전후에 UTC 날짜를 오늘 날짜로 잘못 사용하는지 시험합니다.

## 데이터베이스와 권한 설계

- `public.saju_daily_profiles`: `user_id`(사용자별 한 행), 사용자가 고른 `saju_readings.id`, 변경 버전·시각, **원본 입력이 아닌 계산된 대운 방향·시작 시점·기간**을 저장합니다. 선택한 결과가 같은 사용자 소유인지 DB 제약과 서버 검증으로 확인합니다. 저장 결과 삭제 시 잘못된 연결이 남지 않아야 합니다.
- `public.saju_daily_fortunes`: `user_id`, `fortune_date date`(한국 날짜), 생성 당시 프로필 버전·선택 결과 식별자, 처리 상태, `gemini_attempted_at`, 검증된 결과 `jsonb`, 생성·실패 시각과 최소한의 오류 코드를 저장합니다. `(user_id, fortune_date)` 유일 제약으로 하루 한 건을 보장하고, 사용자·날짜 조회 인덱스를 둡니다. 동시 호출 시 원자적인 상태 선점으로 Gemini 중복 호출을 막습니다.
- 두 공개 스키마 테이블에 RLS(행 단위 접근 제한)를 켭니다. 로그인 사용자는 자신의 프로필·오늘 운세만 조회할 수 있고, 비로그인 사용자는 접근할 수 없습니다. 프로필 지정은 본인 인증·원본 결과 소유권·재입력 일치를 서버에서 검사한 뒤 변경합니다. 운세 생성·상태 변경은 보호된 서버 작업만 할 수 있습니다.
- 여러 사용자의 프로필을 읽고 쓰는 Cron의 Supabase **secret key**는 서버 전용으로 분리합니다. 브라우저용 publishable key나 로그인 쿠키와 혼용하지 않으며, secret key는 코드·Git·로그에 남기지 않습니다. Secret key는 RLS를 우회하므로 조회 대상과 쓰기 대상의 사용자 ID를 서버가 엄격히 확인합니다.
- 계정 삭제, 과거 운세 보존 기간, 기존 저장 결과 삭제 후의 운세 처리 기준은 구현 전에 확인합니다. 이번 화면은 과거 운세 목록을 제공하지 않습니다.

## 구현 순서와 완료 조건

1. 운영자가 1일 전체 **오늘의 운세용** Gemini 호출 상한과 예상 등록자 수를 정합니다. 기존 계정 결과의 실제 두 계정 접근 차단 시험을 마칩니다.
2. 테이블·인덱스·제약·권한을 검토 가능한 마이그레이션으로 만들고 개발 환경에서 적용·확인합니다. 운영 DB에는 검증 후 적용합니다.
3. 서버의 계산·Gemini 응답 검사·중복 방지·Cron 인증을 구현합니다. 비밀값 누락, 중복 실행, 부분 실패, 타임존 경계를 자동 검사합니다.
4. `내 사주` 지정 UI와 오늘의 운세 카드를 구현합니다. 결과 없음·생성 중·실패·완료·계정 전환을 화면에서 확인합니다.
5. `npm run check`, `npm run build`, 실제 두 계정의 본인 결과 접근 제한, 보호된 Cron 시험 호출, 배포 사이트의 예약 실행 기록과 다음 날 09시대 실제 생성을 확인해야 완료입니다. 실제 Gemini 호출은 비용을 발생시키므로 예산 승인 후 소량의 시험 계정으로만 검증합니다.

## 이번 범위에서 제외

- 알림·이메일·푸시, 여러 사주를 모두 매일 생성하기, 과거 운세 목록, 운세 공유·결제, 버튼 클릭 시마다 새 AI 해석 만들기, 건강·재물에 관한 확정적 예언.

## 결정 대기

- 1일 **전체 계정 합계의 오늘의 운세용** Gemini 최대 호출 수·예상 활성 사용자 수·운영 비용 상한과 Vercel 플랜을 확인해야 예약 작업을 활성화할 수 있습니다. 상한 설정이 없으면 Cron에서 Gemini를 호출하지 않습니다. 기존 기본·주제별 사주 해석은 이 상한과 별개입니다.
- 지난 운세의 보존 기간과 프로필 변경 당일의 결과 보관 정책은 구현 전 결정합니다.
